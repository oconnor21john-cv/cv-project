5.6 Results, Analysis and Evaluation

This chapter reports the results of the final statistical benchmark conducted on the deployed version of the application. Following removal of non-producing sources from the live system, the production configuration consisted of a single active source (BBC Food). The evaluation therefore reflects the final deployed architecture rather than earlier prototype states.

5.6.1 Dataset and Analysis Procedure

The benchmark dataset was generated using an automated analysis pipeline over 100 trials (20 queries x 5 repeats x 1 active source). Trial-level and recipe-level outputs were recorded in structured CSV files, including:

- `trial_results.csv`
- `recipe_quality.csv`
- `source_descriptive_summary.csv`
- `analysis_report.md`

For each trial, the system logged query, source label, source status, number of recipes returned, latency, fallback activation, and HTTP status indicators. Recipe-level records captured field completeness and extraction quality attributes.

Because the active system had one source only, the analysis used descriptive statistics with confidence intervals, rather than cross-source inferential comparisons. This is methodologically appropriate: between-group hypothesis testing requires two or more independent groups and is not valid in a one-group deployment setting.

5.6.3 Interpretation

The results indicate strong operational reliability and consistency under the final system scope:

1) Reliability  
No unavailable events occurred in the evaluated configuration and no anti-bot blocks were observed for the active source.

2) Retrieval consistency  
The returned recipe count was deterministic under the benchmark configuration (mean = median = 1.00), indicating stable query behaviour.

3) Data completeness  
The completeness metric remained at 1.00 across runs, showing that required recipe fields were consistently populated.

4) Performance profile  
Latency remained within an interactive range (p50 ~2.4 s; p95 ~3.1 s), with limited tail expansion.

Taken together, the evidence supports the claim that the final production version is stable, predictable, and suitable for user-facing operation within its defined scope.

5.6.4 Data Appropriateness for the Study

The collected dataset is appropriate for evaluating the final deployed system, for three reasons:

- It matches the live architecture used by end users.
- It includes repeated measurements across a broad query set (20 topics x 5 repeats).
- It captures both service-level and content-level indicators (latency, success, completeness).

However, suitability depends on the research claim being made. If the study claim is "the final deployed system is reliable and consistent," the dataset is strong and directly aligned. If the claim is "multi-source aggregation effectiveness," the current dataset is insufficient because only one source is active at deployment.

5.6.5 Areas Requiring Expansion

To improve academic depth and strengthen validity claims, the following extensions are recommended:

1) Expand quality measurement beyond field presence  
Current completeness measures structural presence, not semantic quality. Add a manual quality audit sample (for example, 50-100 recipes) to score instruction correctness, ingredient coherence, and title relevance.

2) Add ground-truth allergen evaluation  
Create a manually labelled subset and report precision, recall, and F1 with bootstrap confidence intervals.

3) Add temporal robustness analysis  
Repeat the 100-trial benchmark on at least 2-3 different days and compare latency and success distributions to address day-to-day variability.

4) Add user-focused evaluation  
Conduct a small usability study (e.g., SUS and task completion rates) to complement system-level metrics.

5) Clarify scope transition in the methodology chapter  
Document explicitly that the project moved from multi-source prototype to single-source production, and justify this as an evidence-based reliability decision.

5.6.6 Threats to Validity

- External validity: Findings generalise primarily to the BBC-only production configuration.
- Construct validity: Completeness is field-based and does not fully capture semantic correctness.
- Temporal validity: Website structures may change over time; periodic re-benchmarking is needed.
- Comparative validity: Between-source inferential claims are not possible in the final one-source dataset.

These constraints should be stated explicitly to avoid overgeneralisation.

5.6.7 Outcome Against Project Aim

Within the final production scope, the project meets its practical objective: it delivers a working recipe retrieval application with strong reliability, consistent performance, and complete extracted outputs. The broader multi-source ambition was narrowed for deployment due source-level instability; however, the final system demonstrates a stronger operational baseline and clearer evaluative evidence.

5.7 Project Evaluation (Link to Next Chapter)

The project evolved from a broad multi-source prototype into a narrower but stable deployed system. This improved reliability and reproducibility, but reduced source diversity. The next chapter should therefore evaluate this trade-off explicitly: stronger practical robustness was achieved at the expense of breadth, and future work should explore reintroducing additional sources under stricter compliance and maintainability controls.
